# 兵棋agent进展汇报

**汇报日期：** 2026-08-06
**项目：** 阿拉曼裁判工作室 - 外部大模型指挥官 AI
**当前模型：** DeepSeek `deepseek-v4-flash`

## 1. 项目方向

目标是在规则裁判完全负责合法性、路径、战斗与状态更新的前提下，让大模型承担战略优先级判断。重点不是让模型从大量动作中自由试错，而是让它在充分理解局面、胜利条件和补给态势后，稳定地选择高价值行动。

当前关注三个指标：终局 VP、非法动作率，以及完整对局的 API 成本与时延。

## 2. 游戏画面与操作体验改进

- 将地图、阶段、当前行动方、VP 和 AI 控制器状态放在同一套回放流程中，玩家可以明确看到当前正在进行的阶段，而不是只看到状态瞬间变化。
- AI 每次只执行一个动作：移动时在地图上聚焦行动单位、展示路线和目的地；战斗时聚焦攻击单位与目标格，并展示攻防、赔率、骰点和结果。
- 补充战斗后的撤退、推进、消灭和补给变化反馈；AI 控制方的强制撤退由规则引擎自动规划，玩家仍能看到实际执行结果。
- 保留动作原因、候选评估和规则裁决日志，便于把“AI 为什么这样走/为什么不攻击”与地图画面对应起来，支持回放和复盘。

## 4. 复杂规则 AI 说明

复杂规则 AI 是项目当前的本地正式对手，不调用外部模型。它使用规则引擎生成合法动作，再结合场景目标、补给、地形、敌军控制区、单位价值和战斗风险进行加权评分。

它与模型指挥官的分工不同：复杂规则 AI 强项是稳定、可复现和规则内的场景化战术；模型指挥官强项是理解结构化局面、形成战略意图和比较多个候选。两者都不能直接修改游戏状态，最终路径、战斗、撤退、补给和 VP 都由同一套裁判执行。

复杂规则 AI 当前具备三类能力：

1. **移动决策：** 根据阵营和场景选择推进、拦截、补给保护或十月轴心国撤出方向，同时惩罚进入敌军控制区、暴露补给单位和破坏补给关系。
2. **战斗决策：** 不只看赔率字符串，而是分析 CRT 六面结果、攻击/防御损失、撤退空间、目标价值和投入兵力风险；当最高分战斗低于阶段门槛时主动 `pass`。
3. **场景策略：** July/September 重点围绕阿拉曼和补给线推进或防守，October 增加按剩余回合组织轴心国向西撤出的策略。

因此，复杂规则 AI 既是模型指挥官的规则侧基线，也是后续评估模型战略选择的参照。当前 Hybrid 仍依赖复杂规则 AI 提供合法动作池和本地裁决，二者不是互相替代关系。

### 4.1 复杂规则 AI 的移动评分例子

假设 Axis 在移动阶段有两个合法动作：一个装甲单位沿道路向阿拉曼推进，距离目标减少 3 格但会进入敌军控制区；另一个补给单位向前移动 2 格，暂时不接敌但能保持前线单位补给。复杂规则 AI 不会只比较谁离目标更近，而会同时计算目标进展、道路节省的移动力、控制区风险、单位价值、补给连续性和剩余回合。因此，补给动作可能因为维持整条补给线而获得更高综合分。

### 4.2 复杂规则 AI 的战斗评分例子

假设两个己方单位都与同一个敌军防守格相邻，AI 会生成单单位攻击和双单位联合攻击，并检查每个候选是否合法。对合法候选，它不仅看 `2:1` 或 `3:1` 的赔率，还会统计 CRT 六个骰面中的防守方损失、撤退、己方损失和交换结果。如果联合攻击有机会打开 VP 目标通路且投入风险可接受，就可能执行；如果最高分低于战斗门槛 `165`，则主动 `pass`，表示当前战果不足以抵消兵力风险。

## 5. 大模型 AI 方案

大模型 AI 采用“模型做战略判断，规则引擎做执行裁判”的分工。模型不直接修改游戏状态，也不自行决定最终路径、战斗结果或胜负；它根据当前局面选择下一步行动，所有动作都必须经过本地规则引擎验证。

模型每次读取结构化上下文，主要包括当前场景、回合、阶段、行动方、剩余回合、双方单位摘要、补给、目标 VP、地形、道路、雷区、敌军控制区、近期日志和本地合法候选。模型返回结构化 JSON：规划阶段返回 `phase_intent`，执行阶段返回 `final_action`；不能指定骰点或绕过规则。

项目保留三种大模型决策方式：

1. **候选模式 A：** 本地生成候选，模型每一步直接选择。稳定且易审计，但每次 `pass` 和重复候选也可能消耗 API 请求。
2. **意图模式 B：** 不提供候选动作，模型根据压缩局面自行提出行动，再通过同一个 `act` 接受或获取规则原因。战略自由度高，但更依赖模型自己形成可执行的目标与路径，回退和时延风险更高。
3. **Hybrid 模式：** 模型每阶段先制定一次意图，本地筛选最多 6 条合法执行方案，模型只在小范围内选择。它保留战略判断，同时由规则引擎控制执行边界，是当前推荐方案。

Hybrid 的价值是把大模型擅长的局面理解和战略取舍，与规则引擎擅长的合法动作枚举、路径计算和战斗裁判结合起来。阶段意图缓存避免每个单位移动都重新解释整盘棋，本地快速 `pass` 避免把没有信息增益的阶段送进网络请求；意图失败时则降级到本地默认意图继续。

### 5.1 完整移动例子：从局面到执行

以下是 seed `1942` 实验第一回合初始移动阶段的简化过程。

**第一步：模型输出阶段意图，而不是直接移动。**

```json
{
  "type": "phase_intent",
  "intent": {
    "type": "pressure",
    "sector": "north",
    "target_hex": "3412",
    "priority_units": ["july-2-10-pzg-01", "july-2-10-pzg-02"]
  }
}
```

该意图表示本阶段重点在北部方向制造压力，并优先考虑两支装甲单位。它还不是可执行路径，坐标、移动力和路线仍由本地规则引擎处理。

**第二步：本地从完整合法池筛选小窗口。**

规则引擎根据北部战区、`3412` 目标格和优先单位提升候选排序，最后只发送最多 6 条执行方案。例如其中一条为：

```json
{
  "type": "move",
  "unit": "july-200-pzg-01",
  "destination": "3412",
  "mode": "normal"
}
```

该候选同时附带距离改善、移动力消耗、控制区风险和补给状态等评估。模型只需比较少量已经合法的方案，而不必自行遍历整张地图。

**第三步：模型选择最终动作，裁判负责执行。**

```json
{
  "type": "final_action",
  "reason": "推进北部装甲，保持对目标的压力",
  "action": {
    "type": "move",
    "unit": "july-200-pzg-01",
    "destination": "3412",
    "mode": "normal"
  }
}
```

规则引擎再次验证单位状态、移动力、路径、控制区和堆叠规则。验证通过后，画面聚焦单位、展示路线和目的地，执行完成后更新状态；下一步决策基于新局面重新生成。

### 5.2 战斗例子：为什么保留联合攻击

假设两个己方单位都与同一个敌军防守格相邻。候选生成器会至少保留单位 A 单独攻击、单位 B 单独攻击、A+B 联合攻击和 `pass`。联合攻击通过 `checkCombat` 后会附带合并攻击力、赔率列、CRT 六面结果和风险摘要。

模型可以选择联合攻击，但不能填写骰点。裁判在执行时生成骰点，画面显示攻击单位、目标格、赔率、骰点、损失、撤退或战后推进；若出现强制撤退，AI 控制方由规则引擎自动规划合法撤退路线。

### 5.3 快速 pass 例子

当一个阶段内所有新鲜单位都已经行动，或者没有非 `pass` 合法执行方案时，本地直接返回：

```json
{
  "type": "pass",
  "reason": "local_fast_pass: no legal non-pass execution candidate"
}
```

这一步不请求模型、不产生工具轮次，但仍写入完整转录。seed `1942` 的 Hybrid 对局中，该机制触发 19 次，总耗时约 15.3 秒；A 模式通常仍会为这些阶段发起模型请求。

### 5.4 双工具协议与 Harness 基线

共享工具库按 `ai/config/agent_methods.yaml` 中的 `tool_profiles` 控制模型可见工具，并从 `ai/config/agent_tools.yaml` 读取统一的工具描述和参数 Schema。新实验默认 `map_and_action`，只公开两个工具：`view_map(focus, target)` 和 `act(action)`。`view_map` 是只读当前局面工具，支持 `overview`、`frontline`、`unit`、`hex` 四种焦点；它不修改状态，也不返回完整合法动作候选池，避免把 Direct/Intent 模式退化为 Candidates。`act` 在不修改局面的前提下完成路径、战斗、堆叠、补给和剧本专属规则校验；合法时返回规范化动作并接受，非法时返回可重试原因。一个 step 接受后，后续工具调用均被拒绝，`proposal_id` 不再暴露给模型。

历史 `single_action` Profile 仍然保留，只公开 `act`，用于复现此前完整局和严格单工具 baseline。旧的 `inspect + evaluate_action + submit_action` 也仅作为 `three_tool_legacy` 保留。三种数据按 `tool_profile` 和比较合同哈希分组，禁止混合统计。

OpenCode、LangGraph 和 PydanticAI 是同一比较合同下的三种 Agent 实现：OpenCode 负责通用 Session 与压缩，LangGraph 把重试路径显式建模为状态图，PydanticAI 使用官方 Agent 和隔离 Python sidecar。模型层负责 profile 解析、能力校验、凭据注入、统一网关、重试、脱敏和 Token 统计；规则桥负责把工具请求交给本地裁判。三层之间不共享具体模型实现。

当前模型档案使用稳定的 `deepseek_flash` ID，记录 `openai_compatible` Adapter、`deepseek-v4-flash`、256K 上下文、6000 输出上限和工具调用能力。后续接入 Qwen、Kimi、GLM 或其他兼容 Chat Completions 的模型，只需增加 profile 和环境变量，不改 Harness 或游戏规则工具。

OpenCode 的 `wargame` Agent 固定最多 6 个 agentic steps，只启用 `view_map`、`act`，关闭 Shell、文件、网络、Task、Todo、MCP、LSP 和子 Agent。LangGraph 和 PydanticAI 也只注册同样两个工具定义。每局使用一个 Harness Session；每个 step 都发送新的压缩局面，当前局面覆盖历史摘要；自动压缩只保留战略目标和行动结果，不把旧坐标当作当前事实。

为避免 OpenCode 的持久 Session 重复保存完整兵力明细，OpenCode 额外使用专用的当前局面投影：保留阶段决策简报、单位索引、关键目标格与前线、规则/胜利条件及 `view_map/act` 协议，去除可由单位索引推导的完整 `forces` 摘要，并限制关键地图条目数量。转录同时记录原始规则上下文字节数和实际进入 Harness 的压缩上下文字节数，框架对照可区分规则信息量与框架历史开销。

模型网关只监听 `127.0.0.1`。OpenCode 获得临时本地令牌，真实 API Key 只在模型网关向上游转发时使用。网关记录原始请求、响应、状态码、耗时、重试、Token 和成本，并对 Authorization、Key、Token 和敏感 Header 脱敏。真实预检转录中未发现 API Key 或本地令牌泄漏。

典型流程是：模型先按需要调用 `view_map` 获取当前结构化战场，再调用 `act(action)`；规则桥返回 `accepted=true + canonical_action` 或 `accepted=false + reason`。前者立即结束当前 step，后者会和地图结果一起进入同一步下一轮模型输入，允许模型在总计 6 次工具预算内修正行动。回放引擎仍会对 canonical action 执行最终裁决；若模型超时、工具循环耗尽或无效输出，则使用本地最高评分合法动作并记录 fallback 原因。

旧三工具 baseline 的初步结论是：通用 Agent 框架能够把复杂规则 AI 作为可信工具层使用，非法动作保持为 0；但自由工具规划会放大轮次、首步探索成本与长 Session 上下文。新的双工具协议保留原子 `act`，因此仍消除了“评估成功但未提交”的问题，同时允许模型按需补读地图。下一步需要在固定模型和 seed 下完成三框架的真实对照，而不是把旧数据与新数据混合。

## 6. AI 方案与上下文管理取舍

| 方案 | 核心方式 | 优点 | 局限 | 当前定位 |
| --- | --- | --- | --- | --- |
| 本地简单规则 AI | 合法动作 + 小型直接评分 | 快、稳定、可复现 | 战略能力有限 | 规则回归基线 |
| 本地复杂规则 AI | 场景、补给、地形、控制区和 CRT 风险评分 | 不依赖网络，战术解释性强 | 依赖人工设计权重，策略多样性有限 | 本地正式对手、模型规则基线 |
| `candidates` A | 大模型每步从本地候选中选动作 | 合法率高，过程容易审计 | 每次 `pass` 也可能请求模型，工具轮次和网络成本较高 | 外部模型基线 |
| `intent` B | 大模型自行形成行动意图，再调用工具验证 | 战略自由度最高 | 工具往返多，输出和延迟不稳定 | 研究模式 |
| `hybrid` | 阶段意图 + 最多 6 条本地合法执行方案 | 兼顾战略多样性、合法率和成本 | 意图偏好可能放大拥挤或重复移动 | 当前外部模型首选 |
| `opencode_harness` | OpenCode Session + `view_map/act` + 本地规则桥 | 通用 Agent Session、压缩与模型连接可独立替换 | 首轮探索与框架上下文开销需实测 | 通用 Agent baseline |
| `langgraph_harness` | 固定状态图 + `view_map/act` + 本地回退 | 地图/拒绝反馈和 fallback 路径显式、可检查 | 无界面图执行仍有框架消息开销 | 图编排 baseline |
| `pydanticai_harness` | 官方 PydanticAI sidecar + `view_map/act` | Python 类型化 Agent 与模型适配能力 | 依赖独立 Python 3.11+ 环境 | Python Agent baseline |

虽然模型支持 256K 上下文，但不建议每一步发送完整原始存档和全部动作。当前做法是由规则引擎保留完整状态和合法性，把上下文压缩为协议、胜利条件、双方部队摘要、地图情报、近期日志和阶段目标；大模型只负责战略优先级与候选选择。

Hybrid 的具体流程是：

1. 本地生成完整合法动作池；若没有非 `pass` 动作，直接执行 `local_fast_pass`，不请求模型。
2. 当前 `turn + phase + side` 没有缓存意图时，模型只返回 `phase_intent`，不允许调用工具或直接返回动作。
3. 本地校验并归一化意图，再按战区、目标格、补给收益、VP 影响、攻击机会和优先单位筛选最多 6 条执行方案，并始终保留 `pass`。
4. 模型从小候选集返回 `final_action`，规则引擎负责最终路径、战斗、撤退、补给、状态和 VP 裁判。
5. 意图请求超时或返回无效 JSON 时，记录原因并使用本地默认意图继续，不让单次网络错误中断对局。

## 7. 当前观察与问题

Hybrid 在运行质量上优于 A：平均单步耗时从 41.8 秒降至 31.2 秒，重试从 81 次降至 53 次，且没有增加非法动作。

但当前仅有一个固定 seed，尚不能证明战略质量提升。同时发现 Hybrid 更倾向于把部队推向 `3510`、`3511`：最拥挤目标格占比从 16.4% 提高到 23.0%，重复移动率从 73.8% 提高到 78.4%。这说明阶段意图和候选筛选会放大局部推进方向，当前评分还缺少对拥挤和低净进展移动的约束。

### 7.1 意图模式 B 的已有对比证据

项目中已有一份 DeepSeek Flash 的 B 模式真实转录，但该局在 25 个外部决策后中途停止，没有终局 VP，因此只能作为运行机制观察，不能作为完整胜率样本。

这份 B 模式转录显示：模型在没有候选动作的情况下，主动提出路径查询、动作评估和战斗检查，并自行选择了北线移动、跨单位联合攻击等动作。它共记录约 70 次工具调用和 91 个模型轮次，平均单步约 60.3 秒，最长约 151 秒，平均上下文约 85.7 KB，出现 4 次 fallback 和 14 次重试。

与正式 Hybrid 对照相比，B 模式的主要特点是：

- **战略自由度更高：** 模型可以提出本地候选池没有预先排序的目标和路线。
- **工具成本更高：** 每一步都可能反复执行 `find_path`、`evaluate_action` 或 `check_combat`，模型轮次明显增加。
- **执行稳定性更弱：** 没有候选窗口约束时，模型更容易重复查询、输出空内容或在多个局部方案之间反复判断。
- **目前不能比较终局质量：** B 只有 partial 对局，暂时只能说明它更灵活但更慢，不能说明它的 VP 高于或低于 A/Hybrid。

因此，现阶段的判断是：B 适合用于发现新策略和研究模型的自由规划能力，Hybrid 适合完整对局和稳定回放。后续如果要正式比较 B，必须在相同 seed 下跑完至少 3 局，并使用与 A/Hybrid 相同的 VP、非法率、回退率和时延指标。

### 7.2 DeepSeek 三 Harness 真实 8-step 预检

固定 `July / Axis / seed 1942 / replicate 1 / direct / single_action / deepseek_flash`，OpenCode、LangGraph、PydanticAI 均完成前 8 个回放动作。三者应用层非法动作和本地 fallback 都为 0，说明统一模型网关、单工具协议和规则桥能够承接真实模型请求。

| PydanticAI | 332.5 秒 | 34.7 / 62.8 秒 | 31 | 12 | 4 | 3 | 694,194 | 多次选择不可达目标，路线判断需要规则反馈 |

本轮还不能作为严格 Harness 排名。虽然三份转录的 `comparison_contract_hash` 相同，但 OpenCode 为解决持久 Session 膨胀，实际发送约 21 KB 的局面投影；LangGraph 和 PydanticAI 仍发送约 85 KB 的完整结构化上下文。下一轮必须让三个 Harness 共用同一个上下文投影和历史策略，或者把上下文 profile 纳入比较合同哈希，否则延迟和 Token 差异无法完全归因于框架。

单工具协议的规则防线工作正常：PydanticAI 和 LangGraph 的非法路径提案均未改变游戏状态，模型随后能够依据规则原因修正；OpenCode 的接受后额外调用也被规则桥以 `an action was already accepted for this step` 拒绝。后续仍应在 Harness 层主动中止同一批剩余工具调用，避免无效 Token 和工具轮次。

### 7.5 LangGraph 首局完整对局

固定 `July / Axis / seed 1942 / replicate 1 / direct / single_action / deepseek_flash`，LangGraph 已从 Turn 1 跑到 Turn 7 的 `final_victory`，不是 8-step 预检或中途停止样本。

| 游戏步骤 / 外部行动 | 154 / 98 |
| 模型步骤回退 | 46 / 98，46.9% |

终局 32 VP 由初始 25 VP、消灭 1 个孤立 Allied 作战单位的 1 VP，以及 Axis 最东补给/部分补给单位推进超过 3400 列的 6 VP 构成。完整运行证明规则桥和本地回退能够在两小时长任务中保持状态一致，最终没有将任何非法模型提案应用到棋盘。

46 次回退中，39 次直接记录为上游 `502`，4 次达到 180 秒步骤上限，3 次以“位于未清除敌方雷区中的单位不能攻击”结束。模型还多次重复不可达移动目标或雷区攻击，说明 Direct + 单工具虽然接口最简单，但当前局面投影没有把“禁止攻击单位”和“已确认不可达目标”提升为足够强的执行约束。

本局运行期间还发现：LangGraph 外层超时最初只做 `Promise.race`，未取消后台图执行，可能让旧步骤继续调用新步骤工具；现已增加 `AbortSignal`、每步独立 bridge 会话和 checkpoint namespace。`act` schema 也已明确 `attackers`、`defender_hexes` 等规范字段，战斗阶段不再因 `target_hex` 等别名连续失败。最后，LangChain caller 与 OpenAI SDK client 的重试均已关闭，重试统一交给本地模型网关；SDK client 配置是在本局结束后补齐，因此本局时延仍包含部分重复请求，必须另做干净复跑验证。

这局不能与 A/Hybrid 的 `33 VP / Draw` 直接做 Harness 排名。A/Hybrid 使用不同策略上下文和旧执行协议，而且本次 LangGraph 遭遇长时间 502。它可以证明“完整运行与故障兜底有效”，也能定位 Direct 单工具的具体问题，但不能单独证明 LangGraph 的战略能力或成本低于其他方案。

## 9. 需要讨论的决策

是否将 Hybrid 作为当前外部模型的默认回放模式。现有单局证据表明它显著降低运行成本且未损害 VP，但在完成多 seed 验证及拥挤/往返惩罚前，结论应限于“运行质量改进”，而不是“胜率提升”。
