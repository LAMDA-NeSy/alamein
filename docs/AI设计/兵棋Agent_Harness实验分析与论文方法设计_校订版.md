# 兵棋 Agent Harness 实验分析与论文方法设计



## 一、项目背景与研究目标

本项目将阿拉曼兵棋规则数字化，并使用大语言模型控制 Axis 一方完成移动、战斗、补给和阶段结束等决策。规则引擎负责最终裁决，模型通过 Agent Harness 获取局面、调用工具并提交行动。

这一任务与常见代码 Agent 或网页 Agent 有明显区别：

- **状态变化快**：单位坐标、补给状态、是否已行动、敌军控制区和阶段权限会在每一步后变化。
- **规则约束强**：语义上合理的行动，仍可能因为路径、雷区、控制区、阶段权限或战斗条件而非法。
- **决策时序长**：一局完整实验包含约 100 个外部模型决策，需要跨阶段、跨回合保持战略一致性。
- **工具反馈可验证**：规则引擎可以准确判断行动是否合法，但模型未必能将自然语言拒绝原因稳定转化为后续约束。
- **最终结果由多方共同贡献**：VP 同时受到模型决策、规则引擎、本地 fallback、快速 pass 和战斗随机性的影响。

因此，当前研究目标不是简单比较“哪个 Agent 框架最好”，而是回答：

> 通用 Agent Harness 为什么会在动态、强规则、长时序环境中失效？如何设计一个规则驱动、状态可靠、预算可控的 Harness，使模型保留战略自主性的同时稳定执行合法行动？

## 二、当前系统与实验对象

### 2.1 统一模型与规则层

- 场景：July。
- 外部模型控制方：Axis。
- 主要模型：DeepSeek Flash。
- 规则随机种子：1942。
- 模型统一通过本地模型网关访问。
- 规则引擎是动作合法性的唯一权威。
- 当前主要工具为 `view_map` 和 `act`。

### 2.2 三种 Harness

- **OpenCode Harness**：复用 OpenCode 的持久会话、工具循环和自动 compaction。
- **LangGraph Harness**：使用显式状态图组织“模型决策 -> 工具执行 -> 拒绝后重试 -> 成功结束或 fallback”。
- **PydanticAI Harness**：使用 PydanticAI Agent 和 Python sidecar，通过 JSONL 与 Node 回放进程通信。

### 2.3 工具合同

`view_map`：读取当前地图概览、前线、单位或格子信息，不改变游戏状态，也不返回完整合法动作候选列表。

`act`：接收模型提出的移动、战斗、退出地图或 pass 行动。规则引擎判断行动是否合法：

- 合法时返回 `accepted=true` 和规范化后的动作。
- 非法时返回 `accepted=false`、拒绝原因和评估信息。
- 非法行动不会改变游戏状态。
- 一个步骤接受动作后，后续行动调用应被拒绝。

`illegal_actions=0` 只表示规则桥没有把非法提案应用到游戏，不表示模型从未提出非法行动。评价模型规则理解能力时，应查看 `invalid_action_attempts / act_calls`，而不是只看应用层非法动作数。

## 三、实验可比性说明

### 3.1 严格可比的 8-step 实验

目前严格可比的是两轮 8-step 测试。每一轮内，三种 Harness 使用相同的场景、模型、seed、决策策略、工具 Profile、上下文 Profile 和比较合同。两轮实验的 `comparison_contract_hash` 因 replicate 不同而不同，但每轮内部三种 Harness 的哈希一致。

| Replicate | Harness | VP | 总耗时 | P50 | P95 | 输入 Token | 非法提案 / act | fallback |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| r1 | OpenCode | 31 | 172.6 s | 16.5 s | 23.2 s | 762,137 | 2 / 10 | 0 |
| r1 | LangGraph | 28 | 220.9 s | 24.3 s | 32.1 s | 71,941 | 1 / 9 | 0 |
| r1 | PydanticAI | 31 | 358.7 s | 31.9 s | 54.0 s | 182,696 | 2 / 10 | 0 |
| r2 | OpenCode | 31 | 156.9 s | 12.8 s | 21.3 s | 705,572 | 1 / 9 | 0 |
| r2 | LangGraph | 25 | 227.8 s | 24.7 s | 38.3 s | 63,894 | 0 / 8 | 0 |
| r2 | PydanticAI | 28 | 213.1 s | 24.6 s | 30.6 s | 170,194 | 1 / 9 | 0 |

这两轮短跑只支持以下描述性观察：

- OpenCode 在这两轮中的延迟最低，但输入 Token 显著高于另外两种实现。
- LangGraph 的模型轮数和输入 Token 较少，但两轮 VP 都较低。
- PydanticAI 的 r1 延迟最高，r2 与 LangGraph 接近，说明单次延迟结论不稳定。
- 两轮都只有一个规则 seed，且每轮只有 8 个动作，不能形成统计显著的框架优劣结论。

### 3.2 完整局不能直接排名

> 实现更新（2026-08-12）：三种 Harness 已改为通过共享 `harness_prompt_contract` 生成相同的 system Prompt、step Prompt 和工具说明；新实验会记录 `harness_prompt_version` 与 `harness_prompt_hash`，并将其写入比较合同。下表中的旧完整局仍属于修复前历史数据，必须重新运行后才能用于比较。

三份最新完整局均使用 `map_and_action`，即都向模型提供 `view_map + act`。因此，“完整局工具合同不同”已经不是主要不可比因素。但是三份完整局仍不满足严格排名条件：

| Harness | 完整局工具 | Prompt 状态 | Prompt hash | comparison contract | 输入 Token |
|---|---|---|---|---|---:|
| OpenCode | `view_map + act` | 旧版双工具 Prompt | `4491911a...` | `3af4aef2...` | 32,229,498 |
| LangGraph | `view_map + act` | 修正版双工具 Prompt | `6731660f...` | `58cdf664...` | 2,054,340 |
| PydanticAI | `view_map + act` | 修正版双工具 Prompt | `6731660f...` | `ee2e728e...` | 4,804,645 |

不可直接排名的原因包括：

- OpenCode 的 Prompt hash 与新版 LangGraph、PydanticAI 不同。
- 三份完整局的 `comparison_contract_hash` 均不相同。
- 每个 Harness 只有一个完整局样本，无法分离模型采样波动。
- fallback、快速 pass、网络错误和各 Harness 的会话实现会共同影响最终 VP。
- PydanticAI 当前 Node sidecar 适配层存在响应关联风险，数据可能受到实现 bug 干扰。

因此，这些完整局适合用于分析失效模式、成本和工程风险，不适合直接写成“OpenCode 胜过 LangGraph”或“PydanticAI 不如 OpenCode”。

## 四、OpenCode Harness：持久上下文的成本与陈旧状态风险

### 4.1 日志事实

OpenCode 完整局结果：

- 34 VP，Draw。
- 118 个外部动作，14 次 fallback，fallback 率为 11.9%。
- 27 次 `view_map`，131 次 `act`。
- 98 次行动被接受，33 次行动被拒绝，`act` 拒绝率为 25.2%。
- 4 次动作接受后仍继续调用工具。
- 输入 / 输出 / 缓存 Token 为 32,229,498 / 261,893 / 30,585,088。
- 总耗时 6,132,507 ms，约 102.2 分钟。
- 触发 5 次自动 compaction；日志显示 compaction 请求体约为 756-780 KB。
- 第一步连续调用 5 次 `view_map`，存在无信息增益的重复观察。

### 4.2 解释与边界

当前 OpenCode 实现为一局游戏维护持久 Session。每一步的新局面、地图返回、模型输出和历史工具结果会进入会话，再由通用 compaction 压缩。

这可以解释 Token 和上下文体积持续增长，但“模型实际引用了错误旧坐标”目前缺少系统计数。因此，现阶段可以确认的是**陈旧状态暴露风险和上下文重复**，不能直接声称已经证明了大量陈旧状态误用。

高缓存 Token 表明部分输入被缓存，但缓存不会消除以下问题：

- 计费与吞吐成本仍受大上下文影响。
- 长历史中同时出现旧坐标和新坐标，增加状态冲突风险。
- 战略信息可能被大量瞬时战术细节稀释。
- 通用 coding-agent compaction 不理解兵棋状态的生命周期。

### 4.3 可提出的方法：权威状态投影

提出 **Authoritative State Projection**：

- 每一步重新构建最小当前状态，并声明它是当前行动的唯一事实源。
- 长期记忆只保存战略目标、已确认规则约束、阶段成果和未完成任务。
- 旧坐标、旧可行动信息、旧补给结果在步骤结束后自动失效。
- 所有局面携带 `state_version`，行动和约束必须引用当前版本。
- 使用兵棋领域 compaction，分别处理战略事实与瞬时战术事实。

### 4.4 待验证假设

与通用持久会话相比，权威状态投影能够在不显著降低 VP 的前提下，减少输入 Token、状态重复率和陈旧状态引用次数。

## 五、LangGraph Harness：约束持久化不足与两轮协议开销

### 5.1 新版完整局日志事实

新版 LangGraph 使用 `map_and_action`：

- 32 VP，Draw。
- 101 个外部动作，30 次 fallback，fallback 率为 29.7%。
- 19 次 `local_fast_pass`。
- 75 次 `view_map`，79 次 `act`。
- 52 次行动被接受，27 次被拒绝，`act` 拒绝率为 34.2%。
- 应用层非法动作数为 0。
- P50 / P95 单步延迟为 48.7 / 126.2 秒。
- 总耗时 6,099,512 ms，约 101.7 分钟。
- 输入 / 输出 / 缓存 Token 为 2,054,340 / 223,106 / 1,166,720。

作为历史对照，旧版 `single_action` 只提供 `act`：

- 32 VP，98 个外部动作。
- 46 次 fallback，fallback 率为 46.9%。
- 84 次 `act` 中 54 次被拒绝，拒绝率为 64.3%。
- 输入 Token 为 721,906。

在当前新旧两次运行中，加入 `view_map` 并更新 Prompt 后，拒绝率从 64.3% 降至 34.2%，fallback 率从 46.9% 降至 29.7%，但输入 Token 增至旧版的约 2.85 倍。两次运行的 VP 都为 32，因此目前只能确认执行层指标改善，不能证明战略质量或胜负表现提升。由于工具 Profile 和 Prompt 同时变化，下降幅度也不能完全归因于 `view_map` 单一因素。

### 5.2 根因修正

旧版出现过同一步连续 6 次提交同类非法攻击。新版中，同一拒绝原因在单个步骤内最多出现 1 次，旧版的单步盲重试没有复现。因此，不能再概括为“LangGraph 必然发生单步盲重试”。

新版仍出现跨步骤重复约束违反：

- “位于未清除敌方雷区中的单位不能攻击”累计出现 8 次。
- `july-200-pzg-01 -> 3611` 不可达累计出现 6 次。

更准确的失效模式是：**规则拒绝没有被编译为带对象、作用域、状态版本和生命周期的阶段级约束，因此同一约束会跨步骤重复触发。**

另外，30 次 `502 This operation was aborted` 多数发生在 `view_map` 返回后、第二次模型请求生成行动时。这说明 `view_map -> 模型再决策 -> act` 的两轮协议扩大了网络请求暴露面。该问题同时涉及模型服务稳定性、网关重试和两轮调用协议，不能全部归因于 LangGraph 状态图。

### 5.3 可提出的方法

**Constraint Compiler and Memory**：

- 将自然语言拒绝解析为结构化约束，而不是原样追加到 Prompt。
- 约束包含规则类型、对象、条件、作用域、来源状态版本、解除条件和到期条件。
- 维护步骤级和阶段级约束集合。
- 同一动作签名在同一 `state_version` 被拒绝后，不允许再次提交。
- 状态变化后重新验证约束，避免永久保存已经失效的禁忌。

示例：

```yaml
type: forbid_attack
unit: july-2-10-pzg-01
condition: uncleared_enemy_minefield
scope: current_phase
state_version: 73
expires_when:
  - minefield_cleared
  - phase_changed
```

**Unified Budget Coordinator**：

- 每一步只设置一个总时间预算和总重试预算。
- 网关重试、模型调用、工具调用和规则拒绝后的再规划共同消耗该预算。
- 根据剩余预算决定继续推理、切换行动类型或触发 fallback。

### 5.4 待验证假设

结构化约束记忆可以显著降低跨步骤重复违反率和 fallback 率；统一预算可以降低 P95 延迟，而不显著降低模型成功提交动作的比例。

## 六、PydanticAI Harness：工具流程成本与 sidecar 事务风险

### 6.1 日志事实

PydanticAI 完整局结果：

- 32 VP，Draw。
- 103 个外部动作，11 次 fallback，fallback 率为 10.7%。
- 19 次 `local_fast_pass`。
- 90 次 `view_map`，139 次 `act`。
- 77 次行动被接受，62 次被拒绝，`act` 拒绝率为 44.6%。
- 2 次动作接受后仍继续调用工具。
- 输入 / 输出 / 缓存 Token 为 4,804,645 / 287,210 / 3,679,872。
- 总耗时 5,991,680 ms，约 99.9 分钟。

### 6.2 工具流程问题

PydanticAI 完整局平均每个外部动作约调用 0.87 次 `view_map`，地图调用频率高于 OpenCode。地图观察并未保证行动合法，仍有 62 次 `act` 被拒绝。

这说明“允许查看地图”不等于“提供当前行动的可行域”。地图适合支持战略理解，但路径、雷区、ZOC 和阶段权限仍需要规则侧验证。

### 6.3 当前项目适配层的正确性风险

当前 Node 侧 `JsonlSidecar` 使用 FIFO 队列关联请求与响应：收到一行响应时直接执行 `pending.shift()`。请求超时后，对应 pending 项会被删除。如果 Python 任务未真正取消、迟到响应随后到达，它可能被错误地交给下一个 pending 请求。

这是**本项目 PydanticAI sidecar 适配层的实现风险**，不是 PydanticAI 框架本身已经被证明存在的缺陷。修复前，相关完整局数据可以用于排查工程问题，但不能作为 PydanticAI 框架能力的可靠证据。

### 6.4 可提出的方法：版本化工具事务

提出 **Versioned Tool Transaction**：

- 每个请求携带 `request_id`、`step_id`、`session_id` 和 `state_version`。
- 响应必须按 `request_id` 显式匹配，禁止依赖 FIFO 顺序。
- 步骤超时后取消或标记对应任务，迟到响应一律丢弃。
- 接受动作后关闭该步骤事务，并拒绝后续工具调用。
- 应用动作前再次校验 `state_version` 和当前阶段。

### 6.5 待验证假设

版本化工具事务能够消除跨步骤响应污染和重复应用动作，并提高 sidecar 异常时的可诊断性；它不一定直接提高 VP，但应显著提高实验结果的可信度。

## 七、三个 Harness 暴露的共同问题

### 7.1 地图可见不等于行动可行

`view_map` 提供战略和战术信息，但不提供完整合法动作候选。模型仍可能提出不可达移动、雷区内攻击或阶段不允许的行动。需要在“全量候选列表”和“纯地图观察”之间提供局部、按需的规则可行域查询。

### 7.2 自然语言错误不能稳定成为约束

规则引擎返回自然语言拒绝原因，但三种通用 Harness 都没有自动将其转化为可执行、可复用、可失效的结构化约束。

### 7.3 fallback 会掩盖模型真实能力

最终 VP 包含本地 fallback 的贡献。高 VP 不等于模型独立完成了高质量决策。报告应同时给出：

- 模型成功提交动作比例。
- fallback 率和 `local_fast_pass` 数量。
- 仅模型控制步骤的结果。
- fallback-adjusted VP 或模型贡献归因指标。

### 7.4 重试预算缺少跨层协调

模型网关、Harness、工具循环和规则拒绝后的再规划可能分别维护重试或超时。局部合理的重试叠加后，会放大延迟和请求量。

### 7.5 瞬时事实缺少生命周期

单位坐标、阶段权限、可达路径和补给结果都有明确生命周期。通用 Agent 记忆通常只区分“保留或压缩”，没有区分“长期战略事实、阶段事实、步骤事实和一次性工具结果”。

## 八、拟提出的统一方法

### 8.1 方法名称

暂定：**Rule-Grounded State-Consistent Harness（RG-SCH）**，即规则驱动、状态一致的 Agent Harness。

### 8.2 总体流程

```text
权威当前状态 + state_version
            |
            v
战略意图 / 局部查询需求
            |
            v
按需局部可行域 + 生效中的结构化约束
            |
            v
模型提出一个行动
            |
            v
规则事务校验 act(action, state_version)
      | accepted            | rejected
      v                     v
事务提交并结束步骤      编译约束并在统一预算内再规划
```

该方法组合五个机制：

1. **权威状态投影**：只让当前版本状态作为行动事实。
2. **局部可行域**：按单位、目标或战区提供有限规则信息，不直接替模型完成战略决策。
3. **结构化约束记忆**：把拒绝原因编译成有生命周期的约束。
4. **统一预算协调**：合并网络、模型、工具和规则重试预算。
5. **版本化工具事务**：确保响应属于正确步骤，合法动作只执行一次。

### 8.3 局部可行域不是候选动作列表

局部可行域只回答模型当前需要的规则问题，例如：

- 某单位能否到达指定关键格。
- 某接触目标有哪些可参加攻击的单位。
- 某移动是否破坏补给或进入敌军 ZOC。
- 某阶段允许哪些行动类型。

它不返回全局排序后的完整行动列表，避免规则引擎替代模型的战略决策。

### 8.4 约束生命周期

建议将约束分为：

- **步骤级**：只对当前 `state_version` 有效，例如某条路径不可达。
- **阶段级**：阶段切换后失效，例如单位当前阶段不能再次行动。
- **条件级**：满足解除条件后失效，例如雷区清除后可以攻击。
- **长期级**：跨回合保留的战略规则或目标。

### 8.5 贡献归因

实验报告需要区分：

- 模型的战略选择贡献。
- Harness 的上下文、工具和重试管理贡献。
- 规则引擎的合法性保障贡献。
- fallback 和快速 pass 的本地策略贡献。
- 随机战斗结果的贡献。

## 九、论文可写的核心研究问题

1. **状态问题**：在动态规则环境中，如何防止持久 Agent 会话中的陈旧瞬时事实污染当前决策？
2. **约束问题**：如何把规则工具的自然语言拒绝转换为可执行、可复用且会正确失效的约束？
3. **事务问题**：如何在长时序异步工具调用中保证响应、状态版本和动作提交的一致性？
4. **自主性问题**：局部可行域应提供多少规则信息，才能降低非法率而不替模型完成战略规划？
5. **评测问题**：如何分离模型、Harness、规则引擎、fallback 和随机性的贡献？

## 十、实验设计

### 10.1 公平对比合同

Harness 对比必须固定：

- scenario、external side、规则 seed。
- model profile 和模型参数。
- Prompt registry hash。
- decision policy 和 context profile。
- tool profile、工具描述、参数 Schema 和最大调用次数。
- 单步时间预算、总重试预算和 fallback 策略。
- 最大游戏步骤和终局条件。

只有 `comparison_contract_hash` 一致的实验，才能用于同一轮 Harness 对比。replicate 不同的实验应作为配对重复样本汇总，不应直接混成同一个合同实例。

### 10.2 建议规模

最低建议：

- 3 个规则 seed。
- 每个 seed 运行 3 个模型 replicate。
- 3 种 Harness。
- 至少 2 个模型 Profile，以检查方法是否只对 DeepSeek Flash 有效。
- 每种设置至少完成一局，短跑只用于预检和调试。

### 10.3 消融实验

- Base Harness。
- Base + 权威状态投影。
- Base + 结构化约束记忆。
- Base + 局部可行域。
- Base + 统一预算。
- Base + 版本化工具事务。
- 完整 RG-SCH。

### 10.4 主要指标

- VP、胜负等级和规则随机结果。
- `act` 接受率与非法提案率。
- 重复违反率：相同规则、单位、目标或动作签名重复被拒绝的比例。
- 模型成功提交动作比例、fallback 率和 `local_fast_pass` 数量。
- 输入、输出、缓存 Token 与估算成本。
- 单步 P50、P95 和最大延迟。
- 模型轮数、地图调用数、行动调用数和无收益工具调用数。
- 状态重复率、陈旧状态引用次数和约束命中率。
- 迟到响应、跨步骤响应、接受后工具调用和重复应用动作次数。
- 过早 pass、重复移动、目标格拥挤和补给破坏。

## 十一、预期论文贡献

1. **问题层贡献**：系统刻画通用 Agent Harness 在动态、强规则、长时序环境中的状态、约束、预算和事务问题。
2. **方法层贡献**：提出 RG-SCH，将权威状态投影、局部可行域、结构化约束记忆、统一预算和版本化工具事务组合成执行框架。
3. **评测层贡献**：提出区分模型、Harness、规则引擎、fallback 和随机性贡献的比较合同与指标体系。
4. **系统层贡献**：在完整兵棋对局中验证方法，而不只使用静态问答或短工具调用任务。

## 十二、当前结论边界与风险

- 严格可比实验只有一个规则 seed、两个 replicate、每个 replicate 仅 8 个动作，统计证据不足。
- 三份完整局虽然都使用 `view_map + act`，但 Prompt hash 和 `comparison_contract_hash` 未统一，不能用于 Harness 排名。
- OpenCode 的 32.2M 输入 Token 受持久 Session、重复上下文和统计口径共同影响，需要进一步计算去重后的有效上下文。
- LangGraph 新旧实验同时改变了工具 Profile 和 Prompt，因此拒绝率下降不能完全归因于 `view_map` 单一因素。
- LangGraph 的 502 同时涉及两轮调用协议、模型服务和网关，不能全部归因于图结构。
- PydanticAI 的响应关联风险位于本项目 Node sidecar 适配层，不能写成 PydanticAI 框架固有缺陷。
- 三份完整局 VP 为 34、32、32，但包含 fallback、快速 pass 和随机战斗贡献，不能作为纯模型能力分数。
- 目前尚未系统统计陈旧状态引用、迟到响应和重复违反率；相关结论应表述为日志支持的风险或案例，而不是总体发生率。

## 附录 B：一句话总结

当前实验没有证明某个 Harness 普遍优于其他框架，但清楚暴露了一个共同缺口：通用 Agent Harness 缺少对动态状态、规则约束、跨层预算和异步事务的一体化管理。论文最有价值的方向，是提出并验证一个 Rule-Grounded Harness，使模型在保留战略自主性的同时，只基于当前真实状态，在规则允许且事务一致的行动空间中决策。
